# 校园供餐多源数据质量与过敏原暴露覆盖分析工具

一款纯浏览器端（React 18 + TypeScript + Vite）的数据分析工具，帮助数据分析师判断多类来源数据——
**供应商成分、菜谱、厨房实际用料、餐次日志、学生饮食限制**，以及本次新增的
**厨房领料、制作批次、窗口发餐日志**——能否可靠关联，并量化过敏原暴露分析中
**多少记录有证据支持、多少存在候选待确认、多少因来源缺失无法判定**；
同时把跨午夜备餐的多源事件**关联到正确的供餐周期**，查清补传与时间更正会改变哪些餐次的分析。

- 不调用任何真实学校服务，不上传个人数据；所有数据保存在浏览器本地 IndexedDB。
- 读取随项目提供的 CSV / JSON 样例（`public/sample-data/`，全部为虚构数据）。
- 未匹配记录一律计入「未知」，**不会被当成「没有过敏原」**；厨房 `PLANNED`（计划使用）不参与实际暴露计算。

## 一、核心设计（过敏原覆盖分析）

### 1. 三桶证据口径（每条领餐记录恰好落入一桶）

| 桶 | 含义 | 进入条件 |
| --- | --- | --- |
| 有证据支持的匹配 `CONFIRMED` | 链接链完整、原料解析有证据 | 供应商**精确编码**、**已批准别名**或分析师**人工确认**，且餐次/用料/限制链路完整 |
| 存在候选但需确认 `CANDIDATE_PENDING` | 有名称/规格/单位/成分候选，但未确认 | 候选**确认前不进入正式统计**，不低报暴露 |
| 来源缺失无法判定 `UNKNOWN_MISSING` | 来源缺失或链接断裂 | 区分空餐次、关联不存在、时间无法归属、批次未到齐、限制为空/未生效等具体原因 |

精确匹配与上下文候选**并行**：只有精确编码/批准别名自动生效；候选经分析师确认后才复用该决定。

### 2. 字段四态（不折叠成同一个失败数）

- `FIELD_NOT_PROVIDED` 源文件未提供该字段（如乙校供应商文件没有 `cert_no` 列）
- `VALUE_EMPTY` 字段值为空（甲校部分行 `cert_no` 留空）
- `REF_NOT_FOUND` 关联对象不存在（领餐→餐次、餐次→菜谱、限制学生→领餐）
- `BATCH_PENDING` 来源批次尚未到齐（`kit-b-2`，预期 6 行）

### 3. 不可变运行与版本固定

每次分析运行固定引用：**全部输入文件 SHA-256、映射版本+修订号、规则版本（rules-v1）**。
补发旧数据或修改映射后生成的是**新运行**，历史运行不被静默改写；「运行对比」页展示三桶迁移矩阵、
覆盖率变化与质量问题增减。

### 4. 映射乐观锁（多标签页）

保存映射时重新读取 IndexedDB 校验修订号；另一标签页已提交更高版本时，后提交者保存被拒绝并提示重载，
已确认映射不会被覆盖（同时通过 `BroadcastChannel` 主动推送版本变化）。

## 二、供餐周期与多源事件时间关联（本次新增）

晚间领出的同一批原料可能用于次日早餐，剩余制成品还可能凭留样和转供记录用于午餐；厨房写的是领料时间，
制作批次写开工和完成时间，窗口日志写实际发餐时间，供应商文件上的日期却只是资料生成日期。
本模块把多源事件关联到**供餐周期**（学校当地日历与业务日），回答「这批用料究竟关联到哪些供餐周期、
补传和时间更正会改变哪些餐次的分析」。

### 1. 四项数据职责（分别维护，互不改写）

| 资料 | 内容 | 维护方式 |
| --- | --- | --- |
| 来源时间设置 | 每个时间字段的**业务含义**（领料/开工/完成/发餐/资料生成日期）、**时区声明**、**精度**、**有凭证的校时区段** | 「供餐日历与时间」页，版本 `ts-vN` + 修订号 |
| 供餐日历 | 学校、窗口、餐别、**业务日**、实际开放区间（可跨午夜）、临时调整 | 同上，版本 `cal-vN` + 修订号 |
| 批次关系 | 领料→制作、制作→发餐的**明确引用**（事件行内）与可补录的**转供记录** | 「批次关系」页，版本 `rel-vN` + 修订号 |
| 关联运行 | 采用的时间解释、日历与资料批次版本，输出**已确认 / 仍有候选 / 时间冲突 / 缺少依据** | 「时间关联运行」页，不可变 |

修改一个窗口的日历**不会悄悄改写其他学校已完成的分析**：每次关联运行固定引用当时的
`ts-vN / cal-vN / rel-vN` 版本与全部输入哈希，更正只会生成新的运行。

### 2. 时间解释口径

- **精度分级**：只写日期的记录规范化为**全天半开区间**（不补成午夜整点）；分钟精度展开为一分钟区间；
  带明确偏移的完整时间戳按原值使用、**不再重复换算**。
- **时区**：未声明时区的本地时间按**学校当地时区**解释，**不借用浏览器设置**；
  分析界面统一按 `+08:00` 显示，显示转换不改变记录属于哪次供餐。
- **校时**：一次校时作用于**有凭证的整段记录**（同一设备同一区段同一偏差，不为每行挑不同偏差）；
  **跨设备的数据不共用同一偏差**。每条事件的原始时间文本、标准化范围、所用校时依据、资料收到时间均可查。
- **日历**：夜宵延长或两个窗口同时开放时允许区间重叠——仅因重叠不判错，也不为唯一归属裁掉真实窗口；
  跨午夜窗口不按午夜机械切成两个供餐日。

### 3. 关联判定口径

1. **先用有依据的批次、窗口及转供引用约束候选，再核对时间关系**；制作完成应早于相应批次发餐，
   领料仅说明物料进入厨房，不能单靠同日或相邻时刻证明实际投料。
2. 明确引用与时间矛盾时**保留冲突并指出涉及的原始行**，不抹掉引用改配另一餐。
3. 缺少明确引用时按学校、厨房、菜品及有效开放区间计算候选；**候选仅说明尚可关联，不自动进入已确认**。
4. 时间误差跨过餐次边界时**保留所有仍成立的候选**；已知批次和窗口足以消除歧义时说明依据；
   不把误差范围的中点当真实发生时刻。
5. 一次制作供应多个窗口/餐次时**保留实际分流关系**；同一发餐事件被多来源重复记载**只计一次**，
   真实的两次发餐即使时间相同也不合并（按物理事件标识 `serving_uid` 去重）。
6. 剩余制成品跨餐次使用**必须有转供依据**；原料保质期或在库状态不能代替；资料不全时保留未知，
   不推断发生过暴露或没有暴露。

### 4. 实现路径选择与成本说明

针对**本地批量导入 + 反复局部更正**的使用方式，主路径选择 **统一排序 + 顺序扫描（整批重建）**：

- **为什么**：每次更正（日历修订、校时更正、补录转供）都生成新的不可变运行，整批重建一次排序、
  一次扫描即可得到全部关联，重复读取可控，且与不可变运行的语义天然一致。
- **代价（在哪里付出等待与空间）**：晚到一条旧事件需要重新整理相关时间段（整批重建一次）；
  排序占用 O(n) 临时空间；大任务分片执行、让出主线程（界面不失去响应，显示处理范围与进度，可取消重跑）。
- **另一条路径**（按学校/窗口/时间范围建索引、按需关联，局部更正快，但跨午夜区间、开放范围修订、
  批次跨餐引用都要同步维护索引，首次导入与大量随机查询有额外开销）**必须产生同样的关联结果**：
  引擎内置逐条暴力对照路径 `correlateRowByRow`，测试固化两条路径在全部样例上**完全一致**，
  运行详情页提供「抽样逐条对照」随时抽查——**不以漏掉跨日/跨窗口边界记录换取速度**。

### 5. 更正与补传的工作流

更正时间解释、补录转供记录或修订日历时：**先展示原归属、候选变化和受影响餐次（影响预览），
再生成新的分析运行**。影响范围同时检查**原时间位置和更正后位置**——记录从原餐次移走时，
两边的计数与未知范围都更新；日历修订还会检查**以前没有任何候选的记录**（新开放窗口可能让它们
首次进入范围）。按入库日查看补传规模只是另一种分析视角，不能替换按实际供餐周期得到的关联。

## 三、目录结构

```
public/sample-data/          随项目提供的样例输入（CSV/JSON + manifest + 种子映射）
  manifest.json              批次清单（含晚到批次 sup-a-2、未到齐批次 kit-b-2、三类事件批次）
  standard_ingredients.json  10 种标准原料及其过敏原
  seed_mappings.json         初始映射（批准别名 + 人工确认决定）
  schoolA/ schoolB/          供应商/菜谱/厨房用料 + 领料记录、制作批次
  meal/                      餐次日志、学生领餐 + 窗口发餐日志
  diet/                      饮食限制
  time/                      来源时间设置、供餐日历、批次关系（三份独立维护的资料）
src/
  lib/        CSV 解析、SHA-256、IndexedDB 封装、数据加载、导出、批次统计、显示时区
  engine/     规则、上下文索引、质量检查、匹配引擎、运行引擎与对比/预览（纯函数，可单测）
    correlation/  时间规范化（精度/时区/校时）、关联引擎（排序扫描+逐条对照双路径）、
                  异步任务运行器（分片/进度/取消/代际）、影响预览与运行差异
  state/      React 全局状态、IDB 持久化、乐观锁、关联任务生命周期
  components/ 共享组件（徽标、抽屉、覆盖图、影响预览）
  pages/      总览 / 来源批次 / 映射工作台 / 质量检查 / 分析运行 / 运行详情 / 运行对比 /
              供餐日历与时间 / 批次关系 / 时间关联运行
Dockerfile + docker-compose.yml + nginx.conf   一键静态部署
```

## 四、本地启动

### 方式 A：Node 开发服务器（推荐用于本地开发）

要求 Node.js 22（容器内固定入口 `/opt/node-22/bin/node`）。

```bash
npm install --registry=https://registry.npmmirror.com
npm run dev        # http://localhost:5173
```

生产构建与本地预览：

```bash
npm run build      # 类型检查 tsc -b + vite build，产物在 dist/
npm run preview    # http://localhost:4173 静态预览（含 SPA 回退）
```

> 必须通过 HTTP 服务访问（需要 `fetch` 读取样例数据），不要直接双击打开 index.html。

### 方式 B：Docker / Compose 一键启动

```bash
docker compose up --build
# 打开 http://localhost:8080
```

多阶段构建：node:22-alpine 构建静态资源 → nginx:1.27-alpine 托管（已配置 SPA 路由回退）。
停止：`docker compose down`。

## 五、测试账号与隐私说明

本工具**没有登录体系、没有后端、没有测试账号密码**：

- 样例学生均为匿名学号（`S-1001` … `S-1023`、`S-9999`），由校医维护的饮食限制按匿名学号生效。
- 所有映射、人工确认、分析快照、时间设置/日历/批次关系修订、关联运行与任务仅写入浏览器
  IndexedDB（库名 `campus-meal-dq`）。
- 「分析运行」页提供「重置工作区」，可清空本地数据并恢复随项目提供的种子数据。
- 可在浏览器 DevTools → Application → IndexedDB 中核查全部本地数据，不存在任何网络上报。

## 六、验证方式（建议操作路径）

### 过敏原覆盖分析（既有）

1. **总览页**：查看来源批次的输入/有效/重复/关联/未知行数与三桶覆盖环形图；点开「指标详情」查看分子、分母、排除条件、来源范围。
2. **来源批次页**：打开 `sup-b-1` 看到 `cert_no` 为「源文件未提供」；打开 `sup-a-1` 看到 3 行「字段值为空」；打开 `kit-b-2` 看到「批次尚未到齐」。
3. **映射工作台**：确认候选「芝麻」→ 预览影响 → 保存并生成新运行（候选 1→0、确认 4→5、未知 19 不变）。
4. **分析运行 → 运行详情 / 运行对比**：三桶筛选、逐层下钻、导出；两个运行对比迁移矩阵。

### 供餐周期时间关联（新增）

首次进入自动生成一次全量关联运行（之后不再自动重复）。建议按以下顺序核对演示场景：

1. **时间关联运行 → 运行详情**：
   - **午夜前领料次日发餐**：`ISSUE:ISS-A-01`（9/4 23:40 领料）已确认归属 `P-A-0905-B`（9/5 早餐），
     抽屉中可见原始文本、KT-A-1 校时区段（-5 分钟）与资料收到时间。
   - **延长夜宵跨午夜**：`SERVING:SE-A-003`（9/5 00:25）初始为**时间冲突**——引用链指向 9/4 夜宵，
     但当时日历夜宵 24:00 已关闭；冲突保留并指出涉及原始行。
   - **同批次跨餐转供**：`PRODUCTION:PB-A-0401` 保留晚餐+夜宵分流关系；`SE-A-002` 凭转供单 TR-A-01 确认。
   - **重复上报**：`SE-A-005` 与 `SE-A-004` 同一物理事件只计一次；`SE-A-006` 同时刻真实另一次发餐不合并
     （唯一发餐 14 次，重复上报 1 条）。
   - **不同时间精度**：`ISS-A-03` 仅日期（全天区间，不补午夜整点）；`SE-A-012` 日期精度保留 3 个候选。
   - **无引用时间邻近**：`ISS-A-04`、`SE-A-010` 只有候选，不自动确认。
   - **两窗口同时开放**：`SE-B-001` 保留早餐+快餐两个候选；`SE-B-002` 凭明确引用确认到快餐窗口。
   - **缺少依据**：`SE-A-007`（跨餐次剩余制成品无转供记录）保留未知，不推断。
2. **供餐日历与时间 → 记录临时调整**：把 9/4 夜宵延长到次日 00:40 → 预览影响
   （`SE-A-003` 冲突→已确认；`SE-A-011` **首次进入范围**；两侧餐次计数都更新）→ 保存并生成新运行。
3. **供餐日历与时间 → 来源时间设置 → 新增校时区段**：补录 WT-A-2 终端 -8 分钟（有凭证）→ 预览影响
   （`SE-A-013` 00:45→00:37 首次进入范围；同设备 `SE-A-010` 共用该区段；其他设备不受影响）→ 保存并生成新运行。
4. **批次关系 → 补录转供记录**：补录 `PB-A-0402 → 9/5 午餐`（留样+转供单）→ 预览影响
   （`SE-A-007` 缺少依据→已确认，**跨周期迁移**到 9/5 午餐）→ 保存并生成新运行。
5. **时间关联运行**：查看任务进度/取消/重新执行；「与上一运行的差异」展示更正前后变化；
   「按入库日」切换补传视角；「抽样逐条对照」确认批处理与逐条计算一致；导出 JSON/CSV（引用同一运行编号）。
6. **刷新页面**：已提交的关联运行与未完成任务状态（中断标记、可重新执行）都从 IndexedDB 恢复。

## 七、样例实际计算结果（本仓库已执行验证）

### 过敏原覆盖（既有，22 项断言固化）

- 领餐记录 **24 条 = 有证据 4 + 候选待确认 1 + 来源缺失未知 19**；4 条已确认记录全部命中真实暴露。
- 质量问题计数：重复键 **4**、缺失键/关联缺失 **4**、单位冲突 **1**、时间无法归属 **2**、多对多连接 **1**。
- 确认「芝麻」候选后：候选 1→0、确认 4→5、未知保持 19。

### 供餐周期时间关联（新增，36 项断言固化）

- 种子状态（cal-v1 / ts-v1 / rel-v1）：27 条事件 = **已确认 16 + 仍有候选 6 + 时间冲突 2 + 缺少依据 3**；
  **唯一发餐 14 次**（15 条发餐事件，1 条重复上报）。
- 日历修订（夜宵延长至 00:40）后：`SE-A-003` 冲突→已确认，`SE-A-011` 首次获得候选，`SE-A-012` 候选 3→4。
- 校时更正（WT-A-2 -8 分钟）后：`SE-A-013` 首次进入范围；同设备记录共用区段，跨设备不共用。
- 补录转供（TR-A-02）后：`SE-A-007` 缺少依据→已确认（9/5 午餐），`PB-A-0402` 保留晚餐+次日午餐分流。
- 排序扫描（批处理）与逐条计算（对照）在种子/修订/更正/补传四种状态下**结果完全一致**。
